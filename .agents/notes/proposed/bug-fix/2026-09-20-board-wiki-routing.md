# Agent Note: 开发板问答漏查 Wiki 的定位与修复建议

Status: proposed

## Problem

用户在 2026-09-20 约 16:20 将 SiFli_Wiki 关联到 SDK 网页问答 Agent，随后询问开发板使用方法，简称和部分完整名称没有产生 Wiki 引用。以下时间均为北京时间。排查只读访问线上数据库、容器日志，并核对线上镜像提交；未修改线上配置或执行部署。

线上镜像与本地提交均为 `82e1e3b62c06f0a0eeb2d1a2973a10b6d8419675`。

### 已核实的证据

- Agent 当前记录最后更新于 16:21:57；日志存在 16:20:35 和 16:21:57 的配置更新请求。更新请求正文日志不完整，不据此还原每次修改的具体字段。
- 16:30:30 的“52-lcd开发板怎么使用”：后端加载 11 个知识库，包含 Wiki；新会话加载 0 条历史。实际 5 次搜索全部限定 SDK_last_52x_web，其中一次查询已包含 SF32LB52-DevKit-LCD 完整型号。
- 16:33:17 的“52-DevKit-LCD开发板怎么使用”：同样加载包含 Wiki 的 11 个库；同一会话加载 13 条历史消息，4 次搜索仍全部限定 SDK 库。
- 16:35:18 的“SF32LB52-DevKit-LCD开发板 怎么用”：同样的 Agent 配置哈希、11 个库，新会话加载 0 条历史。首次搜索覆盖 SDK、两个芯片资料库和 Wiki；Wiki 返回 30 个重排前候选，工具最终返回的资料包含开发板使用指南，最终引用也包含该指南。
- 三次浏览器请求均携带不含 Wiki 的旧 10 库列表，包括成功请求。但 `internal/handler/embed_channel.go` 的 `patchEmbedChatPayload` 清空客户端知识库列表，由后端读取 Agent 当前配置；运行日志证实最终范围是 11 库。
- 该 Wiki 文档于 9 月 17 日处理完成，处于启用状态；未发现本次漏查由刚入库引起的证据。

### 目录生成与缓存排查

`agent_service.go` 每次创建 AgentEngine，按当前配置取得知识库信息；`getKnowledgeBaseInfos` 经 service/repository 直接读取数据库，无目录缓存。`knowledgeBaseScopesForPrompt` 优先采用当前 AgentConfig.KnowledgeBases。`observe.go` 每轮生成 runtime_context，`prompts.go` 遍历全部知识库输出名称、描述、能力及最近两篇文档。句柄压缩只替换标识符，不删除知识库条目。对应时段没有知识库详情读取失败或临时库跳过日志，Wiki 也不是临时库。

因此旧会话和后端关联配置延迟不能解释首次失败；代码路径也不支持模型目录复用旧缓存的假设。但不能声称已经逐字取得历史完整模型输入：原始请求日志在 12000 字节截断，首轮请求总长 54999 字节，用户消息目录未保留在该日志中。截断发生在日志格式化函数，实际 HTTP 请求使用独立的完整 jsonData。

### 已发现的配置矛盾

Agent 自定义提示词规定：“通用知识库只有在其描述或系统映射明确允许用于目标型号时才能查询”，并要求所有补充搜索保持既定范围。

SiFli_Wiki 的名称和描述均仅为 `SiFli_Wiki`，generated_profile 为空。按当前数据库和目录代码，最近两篇展示文档是“SF32LB56xU-硬件设计指南”和“SPI screen parameter configuration”，没有明确的 52 系列适用说明。SDK 库的名称却直接包含 52x。该信息不对称与严格规则共同构成漏选 Wiki 的高置信解释；它不是经过固定输入对照实验验证的唯一因果结论。成功请求同时改变了型号写法和会话，不能把差异全部归于名称。

## Proposal

先修复业务配置中的适用范围表达：依据 Wiki 实际文档，为知识库补充准确的芯片系列和开发板主题描述；在 Agent 提示词中明确跨系列资料库可以检索目标型号，但每条结论必须核对原文型号。开发板使用问题应覆盖相关 SDK 与硬件指南来源，不能把“禁止跨型号结论”扩大为“禁止搜索包含多个型号的资料库”。

先以同一模型、相同配置及空历史对三种问法做对照，再修改配置做回归。保留实际工具选库、进入重排的候选及最终引用，不能只检查回答中是否出现 Wiki 字样。必要时补充仅记录目录条目与配置版本的观测，避免记录整段提示词和敏感正文。

## Alternatives considered

- 简称映射：能提高型号字符串匹配率；但失败请求已经搜索过完整型号，仍只选 SDK，所以不足以解决本次范围漏选。
- 刷新网页或等待配置传播：能处理客户端旧配置，本次确实观察到旧 10 库列表；但服务端主动清空该字段，三次均按 11 库执行，不能作为此次主要修复。
- 无差别搜索全部知识库：最大化覆盖，容易验证 Wiki 能被检索；代价是混入其他芯片资料并增加检索开销。优先明确目标型号和相关资料库的关系。

## Acceptance criteria

- 使用三种原始问法，分别在空历史与延续会话中验证；记录重复运行时选库是否稳定。
- 开发板使用问题能够搜索并引用目标 Wiki 指南，且不把其他芯片文档当成目标板的直接证据。
- 更新 Agent 绑定后，下一请求的有效配置与模型目录一致；客户端旧列表不能覆盖服务端配置。
- 配置修改前后对照保留可审计的工具调用、重排和引用证据。本次尚未执行对照实验或配置修改。

## Risks

描述过宽可能增加跨型号误召回；规则必须允许搜索，同时继续限制结论适用范围。模型选库具有波动，单次成功不构成回归通过。历史完整模型目录不可从截断日志恢复，应区分数据库现状、代码推导与历史直接证据。
