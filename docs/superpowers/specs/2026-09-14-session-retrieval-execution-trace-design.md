# 会话检索执行轨迹设计

## 2026-09-17 扩展：正文、模型输入与最终回答

以下扩展取代原设计中“不保存命中文档正文”的限制。管理员访问范围保持不变。

- 快照版本升级为 2；召回、重排候选增加 `content` 和 `content_source`，保存当次全文。继续保留每阶段 500 项上限及总数/截断标记。
- `generation_context` 步骤记录普通 RAG 合并后加入提示词的片段，以及 Agent 内置知识搜索、分块读取、分块搜索工具加入模型上下文的片段。该记录不表示模型最终采用或引用。
- `answer` 保存最终输出、完成/兜底状态，以及明确引用的片段。新请求在模型引用句柄转换为公开 URL 前记录具体 chunk，避免同一网页多个 chunk 被误判为全部采纳。仅能通过历史文档 URL 匹配的引用标记为 `citation_match=document`，界面说明无法确定具体 chunk。引用关闭或不存在时不推断采纳。
- 旧快照按需从相同会话、相同请求的助手消息恢复回答和已保存引用；补充的正文标记为 `answer_reference`，不冒充原始召回快照。不查询当前文档正文，不改写历史存储。无法恢复的内容显示缺失提示。
- 回答明细提供“查看回答”；轨迹详情展示最终回答、引用片段及逐阶段可展开正文。长文本仅在内容区域滚动，原文按文本转义展示。
- JSON 载荷扩展不需要数据库迁移；普通消息 API 不增加审计轨迹字段。


## 背景与目标

会话管理目前仅向租户管理员展示每次回答的模型用量。管理员无法从历史会话中判断 RAG 实际如何处理问题，例如：问题被改写成什么、每个知识库召回了多少候选、哪些文档和分块命中、重排后的分数和最终选择。

本设计新增仅限管理员使用的检索执行轨迹（retrieval execution trace）。它为每个用户请求持久化一份可审计的快照，覆盖普通知识问答 RAG 管道和 Agent 在回答过程中调用的知识库检索工具。普通聊天用户和既有聊天 API 不会读取或返回这些数据。

## 范围

### 包含

- 每个用户请求的原始问题、问题理解/改写后的查询，以及低召回时生成的本地扩展查询。
- 普通 RAG 管道和 Agent 知识库搜索工具的每一轮检索与重排。
- 每个检索目标的知识库、实际召回数量、候选文档、分块和分数。
- 重排模型、阈值、候选数、模型分、最终综合分、最终选中状态，以及降阈值和回退状态。
- 空召回、跳过、失败和取消请求的状态与脱敏错误摘要。
- 管理员会话详情中的请求列表、分轮时间线和候选文档表。

### 不包含

- 命中文档正文、上下文拼接后的提示词、模型输入或工具参数中的文档内容。
- 普通聊天界面或普通聊天 API 的执行过程展示。
- 对历史会话的回填。
- 对现有模型用量统计口径的改变。

## 数据模型

新增版本化迁移创建独立的 `retrieval_execution_traces` 表。每行代表一个用户请求，而不是一条助手消息：这保证了在生成助手消息之前失败、取消或无结果的请求也可审计。

建议字段如下：

| 字段 | 作用 |
| --- | --- |
| `id` | 轨迹主键 |
| `tenant_id` | 强制租户隔离与查询范围 |
| `session_id` | 会话关联与会话删除级联清理依据 |
| `request_id` | 请求的稳定关联键；租户内唯一 |
| `user_message_id` | 可选的用户消息关联 |
| `assistant_message_id` | 可选的成功/兜底助手消息关联 |
| `status` | `completed`、`empty`、`failed` 或 `cancelled` |
| `trace` | JSONB 轨迹快照 |
| `created_at`、`updated_at` | 审计时间 |

对 `(tenant_id, session_id, created_at)` 和 `(tenant_id, request_id)` 建立索引。SQLite 使用对应的兼容 JSON/文本列类型。会话、消息和租户清理流程必须删除关联轨迹，避免孤立审计数据。

`trace` 的稳定版本化 JSON 结构由以下概念组成：

```text
trace_version
original_query
steps[]
  sequence, kind, status, started_at, completed_at
  query / rewritten_query / expansion_queries[]
  retrievals[]
    knowledge_base { id, name }
    returned_count, captured_count, truncated
    candidates[]
      document { id, name }, chunk_id, retrieval_score
  rerank
    model { id, name }, threshold, candidate_count
    candidates[]
      document, chunk_id, retrieval_score, model_score,
      final_score, selected
  error_summary
```

每个子查询最多保存 500 个候选项。超过上限时保留完整的 `returned_count`，设置 `truncated`，并在管理页明确显示截断；正常 `top_k` 配置下保存完整结果。文档和知识库的名称在请求完成时快照化，即使之后改名或删除，审计记录仍然可读。

## 运行时采集与持久化

请求入口创建一个仅存活于当前请求的 `RetrievalTraceRecorder` 并将其绑定到上下文。采集器使用互斥锁和递增序号写入事件，保证并行知识库检索返回时仍能重放真实的可见执行顺序。

普通 RAG 管道的埋点：

1. 问题理解阶段记录原始问题和改写查询。
2. 检索阶段针对每一个目标和查询扩展记录实际返回数量与候选元数据。
3. 重排阶段记录输入候选、模型/阈值、模型分、综合分和最终选择；降阈值重试和原始结果回退作为独立状态。

Agent 的 `knowledge_search` 工具使用同一采集器。每次工具调用创建独立轮次，记录查询、多目标召回、重排及 MMR 后的最终选择。因此一次 Agent 回答可以在同一轨迹中有多轮检索和重排。

请求结束的统一收尾器批量解析所需知识库和文档名称，生成快照并保存。收尾器会尝试保存 `failed` 和 `cancelled` 轨迹；轨迹采集或保存错误只能记录服务端日志，绝不能中断或改变聊天回答。错误摘要必须经过脱敏，排除凭据、授权头和文档正文。

## 管理员 API 与界面

沿用会话管理现有的管理员鉴权和 `SessionManagementRead` 租户范围。新增的轨迹 API 必须在服务层再次执行同一范围校验，不能只依赖前端入口。

- 现有会话用量详情响应只增加轻量的“是否存在轨迹”提示，避免加载候选列表。
- 新增管理员专用的会话轨迹摘要接口，按请求时间列出状态、原始问题摘要、请求 ID、关联助手消息和轮次数；它也返回没有助手消息的失败/取消请求。
- 新增管理员专用的单请求轨迹详情接口，按需返回该请求的完整快照。
- 任何普通聊天、嵌入式聊天或 API-key 的消息读取接口都不增加轨迹字段。

会话管理详情抽屉增加“执行轨迹”区域。管理员先看到请求列表和状态，点击请求后展开完整时间线：

1. **查询增强**：原问题、改写查询和扩展查询。
2. **召回**：每个知识库的召回数量及候选文档表（知识库、文档名、文档 ID、分块 ID、原始分数）。
3. **重排**：模型、阈值、候选数，以及候选的原始分、模型分、最终分和选中状态。

列表、时间线和表格都应清晰显示空结果、跳过、失败、取消和“候选已截断”。旧会话显示“无执行记录”，不视为错误。

## 兼容性与安全性

- 新表和 API 独立于 `messages.agent_steps`、消息历史与用量字段，避免将管理员审计数据意外暴露给终端用户。
- 所有轨迹读写都携带租户范围；跨租户会话或请求 ID 不可读取。
- 轨迹保存的查询文本可能包含用户输入，因此它遵循会话本身的管理员审计访问边界；不额外复制文档正文。
- API 响应按需加载完整候选，避免会话列表和用量详情因轨迹变大。
- 历史数据保持兼容且不回填；旧记录只显示无轨迹状态。

## 测试与验收

后端测试覆盖：

- 普通 RAG 的改写、查询扩展、并行多知识库召回、重排分数和最终选择。
- Agent 一次回答中的多次知识库检索及重排。
- 空召回、跳过重排、降阈值重试、重排 API 回退、取消和回答前失败。
- 500 项上限、真实数量与截断标记。
- 并行事件的序号和稳定展示顺序。
- PostgreSQL/SQLite 迁移、持久化、会话/消息清理及历史会话兼容。
- 管理员可在本租户读取，非管理员和跨租户请求均被拒绝；普通消息 API 无轨迹字段。

前端测试覆盖管理员详情抽屉中的轨迹摘要、按需详情加载、每轮展开、分数显示、错误/空/截断/旧会话状态。验收时使用一条普通 RAG 会话和一条包含多次 `knowledge_search` 调用的 Agent 会话，确认管理员能从问题增强一直追踪到最终重排选择。
